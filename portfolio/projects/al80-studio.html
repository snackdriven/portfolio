01Problem

The tiny screen needed content controls, clear ownership, and a way for alerts to interrupt. Preparing, transferring, and displaying a picture each needed a separate check.

A browser handles preparation and preview; a local host keeps live content updated.

02Decisions

I arranged the controls, directed AI-assisted implementation, and tested on hardware. One host owns the display: panels supply content, the host rotates them, and alerts interrupt before handing control back.

That made switching, interruptions, and reconnecting part of the test plan. Control placement mattered too: a setting should make sense where someone finds it, with a clear connection to the thing it changes.

03Validation

Device-free protocol checks and a mock transport helped test screen packets before hardware sessions. Then came a very specific disagreement: every image-data block was acknowledged, and the keyboard kept showing the old picture. A physical key combination changed the view but still showed the old image. The transfer logs were answering a different question from the screen.

Letting setup settle and removing the trailing view switch made the new frame stay. I confirmed that on the keyboard.

05Limits

Browser control requires wired WebHID. Historical Bluetooth testing does not establish wireless browser control; the retracted 2.4 GHz claim remains unresolved. These records do not certify the current runtime or universal compatibility.
