Problem

The keyboard has a small screen, lighting, and a keymap. Preparing content, previewing it, sending it to the device, and checking the actual result are different jobs. A convincing browser preview cannot show whether the physical keyboard displayed the new picture.

AL80 Studio brings controls into a browser interface. A local host supports continuously updated screen content. The browser can prepare and preview content offline; sending it requires a device connection.

Decisions and implementation

I shaped control placement, screen behavior, and feature refinement while directing AI-assisted implementation and testing on the hardware. One key decision was screen ownership: a single host process rotates panels, while individual panels provide content without independently writing to the device. Alerts can interrupt the rotation, then return control to it.

That design makes switching, interruptions, and reconnecting part of the behavior under test. A setting also needs to sit where its relationship to the changed feature is clear.

Validation on the keyboard

Device-free protocol checks and a mock transport helped test screen packets before hardware sessions. In one debugging session, transfer logs reported that every image-data block was acknowledged, yet the keyboard still showed an old picture. A physical key combination changed the view and still showed the old image. The logs had established receipt, not display.

The fix added settling time around setup and removed a trailing view switch that advanced past the new card. The corrected sequence was confirmed on the keyboard. That direct feedback turned a vague screen problem into a testable behavior change.

Evidence and result

The public project includes a browser control panel, a local host, source code, and documentation. Its records describe historical on-device checks for screen, lighting, and keymap behavior as well as device-free tests. The display debugging record documents the old-picture failure and confirmation of the corrected sequence.

Limits and lessons

Browser device control uses a wired connection and a WebHID-capable browser. Bluetooth worked in historical testing; an earlier 2.4 GHz success claim was retracted and remains unresolved. The documented hardware checks are historical, not a fresh certification of the current runtime or universal compatibility.

My contribution here is interaction direction, implementation guidance, troubleshooting, and testing. The case does not claim independent firmware authorship or that every line was handwritten.
