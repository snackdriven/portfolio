Personal QA workflow

From scattered context to a defensible verdict.

I designed a personal QA workflow to bring ticket context, prior findings, and release information into runbooks I could actually work from.

Result: Review caught misleading screenshots, environment labels, and saved-state claims.

Designing the handoffs.

I defined tool behavior and acceptance checks, directed AI-assisted implementation, and wrote the QA verdicts.

A ticket rarely arrives with everything needed to test it. I wanted one usable packet: expected behavior, regression risks, and a clear account of what the available sources could establish.

Inside the workflow

Illustrative reconstruction · No workplace data

01 / Source context

Start with the sources.

I checked Jira acceptance criteria against RFCs and implementation details in GitHub, then looked through Slack and conversations for decisions missing from the ticket. Conflicting requirements and unanswered product questions stayed in the notes.

What this stage protects

Missing context stays visible.

If a source couldn’t be checked, the packet had to say so. Unavailable, empty, and disconnected sources needed distinct states.

02 / Preparation

Choose the check before the tool.

I brought expected behavior, prior findings, and regression risks into a runbook. Stored values, server rules, and interface calculations needed different assertions.

A test-layer decision

BMI needed UI coverage.

In care-module planning, stored vital values went into GraphQL checks. BMI was calculated in the interface. Read the test design and coverage limits.

03 / Investigation

Follow the state beyond Save.

In one settings investigation, turning an option off and on, then saving, dropped other choices. I matched recording frames with HAR network logs and compared GraphQL values before and after reload. An unaffected option served as a control.

What this stage protects

A persistence claim needs readback.

Record the action, request, reload, and saved values separately. When the testing environment changed, I kept earlier results labeled with where they actually ran.

04 / Independent review

Try to disprove the claim.

An independent AI reviewer replayed the form logic against recorded request data. I reviewed the evidence and corrected claims that the recordings, environment, or stored state did not support.

A correction this stage caught

A loading screen was labeled as a saved result.

Screenshot review caught the mismatch. The notes retained timing offsets, missing visual evidence, and which recordings hadn’t been watched.

05 / Human decision

Write the verdict with its limits.

I wrote the QA acceptance verdicts. AI generated or assembled the surrounding prose. I kept preparation, investigation, independent review, and the human decision separate, with review before posting.

What this stage protects

Dev coverage stays labeled dev.

Review caught a draft that described a dev control as staging coverage. I corrected the report. When shortening another comment overstated the notes, I added a source check before posting.

This reconstructs the workflow, rather than showing a product interface or workplace artifact. The examples retain their historical coverage limits.

Test design

Put the assertion in the right place.

In care-module planning, I put stored vital values and server-rule checks in GraphQL tests. BMI was calculated in the interface, so an API assertion could not tell me whether it displayed correctly. That belonged in UI coverage.

The June 2026 record separates the states: the vitals API checks had run against dev; the UI checks were still marked pending.

Workflow refinement

Sometimes, remove a stage.

I retired a parallel-work pipeline whose overhead outweighed its help, and moved an unused impact viewer into a screen I already used.

The Kanban board moved from ownership lanes to pipeline stages. I removed realistic sample cards from the starting view so they couldn’t be mistaken for work waiting to be done. One writer per shared document and recovery steps for interruptions kept the handoffs manageable.

Outputs

Useful work, with the limits attached.

The workflow produced ticket-specific runbooks and evidence reviews. The release-reporting tools combined Jira status, GitHub pull requests, and release discussions into scope and merge updates in Google Docs and Confluence. Colleagues used those documents to follow releases. I operated the tools; colleagues used the documents.

Limits and lessons

Keep the unfinished work visible.

This was personal tooling for my QA work. The workflows evolved; I later retired the release-documentation automation. Its history included stale information and environment mix-ups that needed correction.

I keep coming back to two questions: can I start work from this packet, and can I tell what it hasn’t checked?
