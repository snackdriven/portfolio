Personal QA tooling

Turning scattered context into reviewable QA work

A personal QA workspace with version control and strong opinions about how AI should behave. I designed the workflow to bring ticket context, prior findings, and release information into runbooks I could actually work from.

Result: A workflow whose review caught misleading screenshots, environment labels, and saved-state claims.

01Problem

A ticket rarely arrives with everything needed to test it. The useful context might be in a code change, an old finding, a discussion, or a release note. I kept having to reconstruct the task before I could investigate it.

I wanted that groundwork in one usable packet: what should happen, what had gone wrong before, where to look for regressions, and which sources the system could not check. Missing context needed a label, not a confident guess.

02Decisions

I defined the behavior, configured the tools, and directed AI-assisted implementation. I tested the runbooks, investigation tools, and evidence-review views on real tasks, then refined how they worked together.

If a source couldn't be checked, the packet had to say so. An unavailable system and an empty result mean different things. I kept preparation, investigation, independent review, and the human decision separate.

I checked Jira acceptance criteria against RFCs and implementation details in GitHub, then looked through Slack and conversations for decisions missing from the ticket. Conflicting requirements and unanswered product questions stayed in the notes.

When instructions changed the testing environment, I kept earlier results labeled with where they actually ran. A reproducible result still needed checking against the intended behavior.

I used one writer per shared document, review before posting, and recovery steps for interrupted work. Those practices needed testing and revision as the tools changed.

I changed the Kanban board from ownership lanes to pipeline stages so I could see progress. Stale, missing, disconnected, and empty data each needed their own state. I removed realistic sample cards from the starting view so they couldn't be mistaken for work waiting to be done.

03Test layers

In care-module planning, I put stored vital values and server-rule checks in GraphQL tests. BMI was calculated in the interface, so an API assertion could not tell me whether it displayed correctly. That belonged in UI coverage.

The June 2026 record separates the states: the vitals API checks had run against dev; the UI checks were still marked pending. A test plan is useful. Calling it a passing suite would be less useful.

04Validation

In one settings investigation, turning an option off and on, then saving, dropped other choices. I used AI-assisted checks to match recording frames with HAR network logs and compare GraphQL values before and after reload. An unaffected option served as a control.

Screenshot review caught a loading screen labeled as a saved result. The notes kept the timing offsets, missing visual evidence, and which recordings hadn't been watched. A screenshot gets a vote, not the final word.

An independent AI reviewer replayed the form logic against the recorded request data. Review also caught two claims that needed correcting:

  • A control ran on dev, but the draft described it as staging coverage.
  • The visible defaults were restored, but the stored settings differed from the starting state.

I corrected the report. When shortening another comment overstated the notes, I added a check against the source before posting.

I asked for more random trials after a repaired pilot passed its original sample. An unused impact viewer moved into a screen I already used, and I retired a parallel-work pipeline whose overhead outweighed its help. Sometimes the useful improvement was one less thing to maintain.

05Evidence

Evidence
Runbooks and evidence reviews; release documents used by colleagues
Status
Workflows evolved; release-documentation automation retired

The workflow produced ticket-specific runbooks and evidence reviews. The release-reporting tools combined Jira status, GitHub pull requests, and release discussions into scope and merge updates in Google Docs and Confluence. Colleagues used those documents to follow releases.

I wrote the QA acceptance verdicts. AI generated or assembled the surrounding prose. I operated the tools; colleagues used the documents.

06Limits

This was personal tooling for my QA work. I later retired the release-documentation automation. Its history included stale information and environment mix-ups that needed correction.

I keep coming back to two questions: can I start work from this packet, and can I tell what it hasn't checked?
